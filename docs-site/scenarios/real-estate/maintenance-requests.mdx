## Persona

**Role**: Software engineer at a property management company overseeing 50+ residential buildings.

The maintenance team currently tracks requests through a shared email inbox. Work orders are assigned by phone, and there is no systematic way to evaluate vendor performance. The team needs a structured system to capture tenant requests, dispatch work orders, and track vendor reliability.

## Business Problem

Maintenance requests get lost in email threads, tenants receive no status updates, and property managers lack data on response times and vendor quality. Emergency repairs compete with routine maintenance for attention without any priority system. This scenario builds a maintenance workflow that captures requests with priority levels, generates trackable work orders, and links vendors to their performance history.

### Step 2. Prepare the decision

- **Goal:** Turn the captured context into the next best action for Maintenance Requests without forcing the human reviewer to assemble the case manually.
- **Required data:** MaintenanceRequest state and history; WorkOrder fields such as scheduledDate, completedDate, cost, and status.
- **AI support:** Run background summarisation, extraction, classification, recommendation drafting, and answer generation so a reviewer sees a prepared case instead of raw fragments. EAI delivers the structured records and AI workflow hooks for this today; specialised scoring engines, external rules, or advanced reasoning controls may still need integration work.
- **Business impact:** Reduce cycle time, improve quality and consistency, and protect the mission-critical metric before the case moves into execution.
- **EAI delivery:** Link records across the scenario, persist decision state as resources, and use workflow actions plus chat assistance to keep humans in control while AI prepares the work.

### Step 3. Execute and collaborate

- **Goal:** Coordinate the actual work, handoffs, approvals, and user updates needed to deliver the service or outcome.

- **EAI delivery:** Use linked object types, actions, resource updates, and workflow-triggered AI assistance so the team can execute in one model instead of splitting work across disconnected tools.

### Step 4. Resolve, explain, and improve

- **Goal:** Close the loop with a clear outcome, an understandable explanation, and feedback that improves the next case.
- **Required data:** final status, outcome, audit history, and follow-up signals across MaintenanceRequest, WorkOrder, and Vendor.

## EAI Platform Support By Step

EAI provides the safe service boundary for Maintenance Requests through Object Types, tenant-scoped resources, document processing, chat workflows, and CLI verification. For this scenario, the main records are `MaintenanceRequest`, `WorkOrder`, and `Vendor`.

| Process step | What EAI provides | Calling pattern |
| ------------ | ----------------- | --------------- |
| Step 1. Capture demand and context | Tenant-scoped intake resources for MaintenanceRequest context such as property, tenant, description, and priority. Object Type validation, starter forms, optional document intake, and chat-guided capture keep the first record complete. | Define fields in `src/eai.config/object-types.ts`, run `eai types validate` and `eai types seed`, create initial `MaintenanceRequest` records with `useResources('MaintenanceRequest')` or `eai resources create MaintenanceRequest`, and keep browser calls behind `/api/eai/...`. |
| Step 2. Prepare the decision | Linked resource queries over MaintenanceRequest state and history; WorkOrder fields such as scheduledDate, completedDate, cost, and status. Search, schema checks, document classification or RAG indexing, and chat summaries turn raw context into a prepared decision. | Use `useResources('MaintenanceRequest')` list/query/search patterns, verify shape with `eai resources schema`, use `useDocuments().upload/classify/ragIndex`, `eai docs upload`, `eai docs classify`, and `eai docs index` where supporting material exists, and send decision-support prompts through `useChat(workflowId, 'chat')` or `eai chat send`. |
| Step 3. Execute and collaborate | Resource updates and actions for WorkOrder actions such as completeWork; Vendor fields such as name, specialty, rating, and contact. Status changes, assignments, notes, generated work packets, and chat support keep humans in control during execution. | Model actions in the Object Type code, call `client.resources.executeAction(type, id, action)` or the app hook equivalent, update records through the app service layer, and verify with `eai resources get/list/query`. |
| Step 4. Resolve, explain, and improve | Outcome resources for final status, outcome, audit history, and follow-up signals across MaintenanceRequest, WorkOrder, and Vendor. Audit-friendly links, indexed final documents, reporting snapshots, and answer generation make the result explainable and reusable. | Persist outcomes as resources, index final material with `eai docs index` or `useDocuments().ragIndex`, send explanation prompts with `useChat` or `eai chat stream`, and use `eai resources aggregate/search` for reporting checks. |

## Prompt, Code, And Service Pattern Mapping

The Object Type code example on this page is the implementation contract for the EAI platform services. eai-gofer should read that code as the source of truth for which resource, document, and chat calls belong in the app.

Use this prompt shape when asking eai-gofer or another coding agent to implement the scenario:

```text
Use the EAI App Template. Model Maintenance Requests with Object Types for MaintenanceRequest, WorkOrder, Vendor. Use useResources for records and actions, useDocuments for uploads/classification/RAG where documents appear, useChat for workflow assistance, and verify with eai types/resources/docs/chat commands. Use eai publicapi only when no named command covers the required platform call.
```

| Scenario artifact | How it maps to EAI service calls |
| ----------------- | -------------------------------- |
| Four-step process | Step 1 becomes resource creation, Step 2 becomes resource query/search plus optional document or chat preparation, Step 3 becomes resource update/action calls, and Step 4 becomes outcome persistence plus explanation/reporting calls. |
| Object Type definitions | `eai types validate`, `eai types seed`, and `eai resources schema` make the model available and checkable before UI work starts. |
| Properties and indexes | Fields become `useResources` payloads, filters, list views, and `eai resources create/list/query/search` checks. Indexed fields should support lookup and triage, not duplicate canonical records. |
| Links between Object Types | Relationships become linked-resource UI, timeline context, and audit trails that app code loads through resource queries rather than separate bespoke stores. |
| Actions and status fields | Workflow buttons and operator transitions call resource action/update helpers, then verify state with `eai resources get/list/query`. |
| Document and chat prompts | Prompts should call the platform documents and chat patterns: `useDocuments().upload/classify/ragIndex`, `eai docs upload`, `eai docs classify`, and `eai docs index` for documents, and `useChat`, `eai chat send`, or `eai chat stream` for conversational assistance. |

## Object Types

| Name | Key Properties | Links | Actions |
|------|---------------|-------|---------|
| **MaintenanceRequest** | `property` (text), `tenant` (text), `description` (text), `priority` (select: emergency, high, medium, low), `status` (select: open, assigned, completed) | one-to-many → WorkOrder | `assignRequest` |
| **WorkOrder** | `scheduledDate` (date), `completedDate` (date), `cost` (number), `status` (select: pending, in-progress, completed, cancelled) | many-to-one → MaintenanceRequest, many-to-one → Vendor | `completeWork` |
| **Vendor** | `name` (text), `specialty` (text), `rating` (number), `contact` (text), `hourlyRate` (number) | one-to-many → WorkOrder | -- |

## CLI Workflow

<Steps>

1. **Scaffold the project**

   ```bash
   eai init maintenance-requests
   ```

2. **Authenticate and pull environment**

   ```bash
   eai login
   eai env pull --include-secrets
   ```

   <Aside type="note">
     If you are an external developer, see [Configuration](/docs/configuration) for login and local environment setup.
   </Aside>

3. **Define your Object Types**

   Create the MaintenanceRequest, WorkOrder, and Vendor types in `src/eai.config/object-types.ts` (see code example below).

4. **Validate the type definitions**

   ```bash
   eai types validate
   ```

   ```
   Tenant: maintenance-requests
   ✔ MaintenanceRequest — 5 props, 1 link, 1 action
   ✔ WorkOrder — 4 props, 2 links, 1 action
   ✔ Vendor — 5 props, 1 link, 0 actions

   ✔ All Object Types are valid
   ```

5. **Seed types to the platform**

   ```bash
   eai types seed
   ```

6. **Create sample resources**

   ```bash
   eai resources create MaintenanceRequest --data '{"property": "Building A, Unit 12", "tenant": "John Smith", "description": "Leaking kitchen faucet", "priority": "medium", "status": "open"}'
   ```

7. **Start local development**

   ```bash
   eai dev
   ```

</Steps>

## Code Example

```typescript
// src/eai.config/object-types.ts
export const objectTypes = {
  'maintenance-requests': [
    {
      name: 'MaintenanceRequest',
      displayName: 'Maintenance Request',
      description: 'A tenant-submitted maintenance request for a property',
      properties: [
        { name: 'property', type: 'text' as const, required: true, indexed: true },
        { name: 'tenant', type: 'text' as const, required: true },
        { name: 'description', type: 'text' as const, required: true },
        { name: 'priority', type: 'select' as const, required: true, options: [
          { label: 'Emergency', value: 'emergency' },
          { label: 'High', value: 'high' },
          { label: 'Medium', value: 'medium' },
          { label: 'Low', value: 'low' },
        ]},
        { name: 'status', type: 'select' as const, required: true, defaultValue: 'open', options: [
          { label: 'Open', value: 'open' },
          { label: 'Assigned', value: 'assigned' },
          { label: 'Completed', value: 'completed' },
        ]},
      ],
      linkTypes: [
        { name: 'workOrders', targetObjectType: 'work-order', cardinality: 'one-to-many' as const },
      ],
      actions: [
        {
          name: 'assignRequest',
          displayName: 'Assign Request',
          description: 'Assign a maintenance request to a vendor via work order',
          requiredRole: 'tenant-staff',
          validationRules: { requiredStatus: 'open' },
          sideEffects: [
            { type: 'set_field', field: 'status', value: 'assigned' },
          ],
        },
      ],
      status: 'published' as const,
    },
    {
      name: 'WorkOrder',
      displayName: 'Work Order',
      description: 'A dispatched work order assigned to a vendor',
      properties: [
        { name: 'scheduledDate', type: 'date' as const, required: true, indexed: true },
        { name: 'completedDate', type: 'date' as const, required: false },
        { name: 'cost', type: 'number' as const, required: false },
        { name: 'status', type: 'select' as const, required: true, defaultValue: 'pending', options: [
          { label: 'Pending', value: 'pending' },
          { label: 'In Progress', value: 'in-progress' },
          { label: 'Completed', value: 'completed' },
          { label: 'Cancelled', value: 'cancelled' },
        ]},
      ],
      linkTypes: [
        { name: 'request', targetObjectType: 'maintenance-request', cardinality: 'many-to-one' as const },
        { name: 'vendor', targetObjectType: 'vendor', cardinality: 'many-to-one' as const },
      ],
      actions: [
        {
          name: 'completeWork',
          displayName: 'Complete Work',
          description: 'Mark a work order as completed by the vendor',
          requiredRole: 'tenant-user',
          validationRules: { requiredStatus: 'in-progress' },
          sideEffects: [
            { type: 'set_field', field: 'status', value: 'completed' },
            { type: 'set_timestamp', field: 'completedDate' },
          ],
        },
      ],
      status: 'published' as const,
    },
    {
      name: 'Vendor',
      displayName: 'Vendor',
      description: 'A maintenance vendor or contractor',
      properties: [
        { name: 'name', type: 'text' as const, required: true, indexed: true },
        { name: 'specialty', type: 'text' as const, required: true },
        { name: 'rating', type: 'number' as const, required: false },
        { name: 'contact', type: 'text' as const, required: true },
        { name: 'hourlyRate', type: 'number' as const, required: false },
      ],
      linkTypes: [
        { name: 'workOrders', targetObjectType: 'work-order', cardinality: 'one-to-many' as const },
      ],
      actions: [],
      status: 'published' as const,
    },
  ],
};
```

## Key Takeaways

- **Priority-based triage**: Maintenance requests are categorized by severity, ensuring emergency issues are routed ahead of routine repairs.
- **Vendor accountability**: Linking work orders to vendors with ratings and cost tracking enables data-driven vendor selection over time.
- **End-to-end traceability**: Every request flows from tenant submission through assignment to completion, with timestamped status transitions at each step.
- **Cost visibility**: Recording costs on work orders gives property managers real-time insight into maintenance spend per building and vendor.
