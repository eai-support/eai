## Persona

**Role**: Backend developer at a commercial real estate firm managing 300+ active lease agreements.

The firm needs a system to track lease terms, automate renewal reminders, and reconcile monthly rent payments. The current process relies on calendar reminders and manual bank statement matching, leading to missed renewals and late payment follow-ups.

## Business Problem

Commercial leases involve complex terms, escalation clauses, and renewal windows that span months. When renewal deadlines are missed, tenants default to month-to-month arrangements at unfavorable rates. Payment reconciliation against lease terms is entirely manual. This scenario builds a lease management workflow that tracks agreements, surfaces upcoming renewals, and links payments to their corresponding lease periods.

## EAI Platform Support By Step

EAI provides the safe service boundary for Lease Management through Object Types, tenant-scoped resources, document processing, chat workflows, and CLI verification. For this scenario, the main records are `LeaseAgreement`, `Renewal`, and `Payment`.

| Process step | What EAI provides | Calling pattern |
| ------------ | ----------------- | --------------- |
| Step 1. Capture demand and context | Tenant-scoped intake resources for LeaseAgreement context such as property, tenant, terms, and startDate. Object Type validation, starter forms, optional document intake, and chat-guided capture keep the first record complete. | Define fields in `src/eai.config/object-types.ts`, run `eai types validate` and `eai types seed`, create initial `LeaseAgreement` records with `useResources('LeaseAgreement')` or `eai resources create LeaseAgreement`, and keep browser calls behind `/api/eai/...`. |
| Step 2. Prepare the decision | Linked resource queries over LeaseAgreement state and history; Renewal fields such as proposedTerms, proposedRent, status, and dueDate. Search, schema checks, document classification or RAG indexing, and chat summaries turn raw context into a prepared decision. | Use `useResources('LeaseAgreement')` list/query/search patterns, verify shape with `eai resources schema`, use `useDocuments().upload/classify/ragIndex`, `eai docs upload`, `eai docs classify`, and `eai docs index` where supporting material exists, and send decision-support prompts through `useChat(workflowId, 'chat')` or `eai chat send`. |
| Step 3. Execute and collaborate | Resource updates and actions for Renewal actions such as acceptRenewal; Payment fields such as amount, dueDate, paidDate, and status. Status changes, assignments, notes, generated work packets, and chat support keep humans in control during execution. | Model actions in the Object Type code, call `client.resources.executeAction(type, id, action)` or the app hook equivalent, update records through the app service layer, and verify with `eai resources get/list/query`. |
| Step 4. Resolve, explain, and improve | Outcome resources for final status, outcome, audit history, and follow-up signals across LeaseAgreement, Renewal, and Payment. Audit-friendly links, indexed final documents, reporting snapshots, and answer generation make the result explainable and reusable. | Persist outcomes as resources, index final material with `eai docs index` or `useDocuments().ragIndex`, send explanation prompts with `useChat` or `eai chat stream`, and use `eai resources aggregate/search` for reporting checks. |

## Prompt, Code, And Service Pattern Mapping

The Object Type code example on this page is the implementation contract for the EAI platform services. eai-gofer should read that code as the source of truth for which resource, document, and chat calls belong in the app.

Use this prompt shape when asking eai-gofer or another coding agent to implement the scenario:

```text
Use the EAI App Template. Model Lease Management with Object Types for LeaseAgreement, Renewal, Payment. Use useResources for records and actions, useDocuments for uploads/classification/RAG where documents appear, useChat for workflow assistance, and verify with eai types/resources/docs/chat commands. Use eai publicapi only when no named command covers the required platform call.
```

| Scenario artifact | How it maps to EAI service calls |
| ----------------- | -------------------------------- |
| Four-step process | Step 1 becomes resource creation, Step 2 becomes resource query/search plus optional document or chat preparation, Step 3 becomes resource update/action calls, and Step 4 becomes outcome persistence plus explanation/reporting calls. |
| Object Type definitions | `eai types validate`, `eai types seed`, and `eai resources schema` make the model available and checkable before UI work starts. |
| Properties and indexes | Fields become `useResources` payloads, filters, list views, and `eai resources create/list/query/search` checks. Indexed fields should support lookup and triage, not duplicate canonical records. |
| Links between Object Types | Relationships become linked-resource UI, timeline context, and audit trails that app code loads through resource queries rather than separate bespoke stores. |
| Actions and status fields | Workflow buttons and operator transitions call resource action/update helpers, then verify state with `eai resources get/list/query`. |
| Document and chat prompts | Prompts should call the platform documents and chat patterns: `useDocuments().upload/classify/ragIndex`, `eai docs upload`, `eai docs classify`, and `eai docs index` for documents, and `useChat`, `eai chat send`, or `eai chat stream` for conversational assistance. |

## Object Types

| Name | Key Properties | Links | Actions |
|------|---------------|-------|---------|
| **LeaseAgreement** | `property` (text), `tenant` (text), `terms` (text), `startDate` (date), `endDate` (date), `monthlyRent` (number), `status` (select: draft, active, expired) | one-to-many → Renewal, one-to-many → Payment | `executeLease` |
| **Renewal** | `proposedTerms` (text), `proposedRent` (number), `status` (select: pending, accepted, declined), `dueDate` (date) | many-to-one → LeaseAgreement | `acceptRenewal` |
| **Payment** | `amount` (number), `dueDate` (date), `paidDate` (date), `status` (select: pending, paid, overdue, waived) | many-to-one → LeaseAgreement | `recordPayment` |

## CLI Workflow

<Steps>

1. **Scaffold the project**

   ```bash
   eai init lease-management
   ```

2. **Authenticate and pull environment**

   ```bash
   eai login
   eai env pull --include-secrets
   ```

   <Aside type="note">
     If you are an external developer, see [Configuration](/docs/configuration) for login and local environment setup.
   </Aside>

3. **Define your Object Types**

   Create the LeaseAgreement, Renewal, and Payment types in `src/eai.config/object-types.ts` (see code example below).

4. **Validate the type definitions**

   ```bash
   eai types validate
   ```

   ```
   Tenant: lease-management
   ✔ LeaseAgreement — 7 props, 2 links, 1 action
   ✔ Renewal — 4 props, 1 link, 1 action
   ✔ Payment — 4 props, 1 link, 1 action

   ✔ All Object Types are valid
   ```

5. **Seed types to the platform**

   ```bash
   eai types seed
   ```

6. **Create sample resources**

   ```bash
   eai resources create LeaseAgreement --data '{"property": "Suite 400, 100 Main St", "tenant": "Acme Corp", "terms": "36-month NNN", "startDate": "2025-01-01", "endDate": "2027-12-31", "monthlyRent": 8500, "status": "active"}'
   ```

7. **Start local development**

   ```bash
   eai dev
   ```

</Steps>

## Key Takeaways

- **Renewal pipeline**: Linking renewals to lease agreements surfaces upcoming deadlines and prevents costly month-to-month rollovers.
- **Payment reconciliation**: Each payment is linked to its lease, enabling automated matching against expected rent amounts and due dates.
- **Structured transitions**: The `executeLease` and `acceptRenewal` actions enforce proper sequencing so agreements cannot be activated or renewed out of order.
- **Audit-ready records**: Timestamped payment records and status transitions create a clear audit trail for financial reporting.
