## Overview

The data model in EnterpriseAI is built on a single core abstraction: the **Object Type**. An Object Type defines a category of resource in your domain -- a `Patient`, a `LoanApplication`, a `Permit`. Everything else (properties, links, actions, side effects) hangs off that definition.

This is **schema-driven development**. You declare what your data looks like, how it relates to other data, what operations users can perform, and what happens automatically when those operations run. The platform enforces all of it.

## Object Types

An Object Type is a named, versioned schema definition. It contains:

- A **name** (PascalCase, e.g., `Patient`, `LoanApplication`)
- A **display name** (human-readable label)
- A **description** (optional documentation)
- A **status** (`draft`, `published`, or `deprecated`)
- A list of **properties** (fields)
- A list of **link types** (relationships to other Object Types)
- A list of **actions** (business operations)

```typescript
const patientType: ObjectTypeDefinition = {
  name: 'Patient',
  displayName: 'Patient',
  description: 'A patient in the intake system',
  status: 'published',
  properties: [ /* ... */ ],
  linkTypes: [ /* ... */ ],
  actions: [ /* ... */ ],
};
```

Object Types are defined in TypeScript files at `src/eai.config/object-types.ts` and pushed to the platform with `eai types seed`.

## Properties

Properties are the fields of an Object Type. Each property has a name, a type, and optional constraints.

### Field Types

| Type | Description | Example Value |
|---|---|---|
| `text` | Free-form string | `"Jane Doe"` |
| `number` | Numeric value (integer or decimal) | `42`, `98.6` |
| `boolean` | True or false | `true` |
| `date` | ISO 8601 date string | `"2025-03-15T10:30:00Z"` |
| `select` | One of a predefined set of options | `"active"` |
| `json` | Arbitrary JSON object | `{ "key": "value" }` |
| `file` | File reference | `"uploads/doc.pdf"` |
| `relationship` | Reference to another resource | `"abc-123-def"` |

### Property Definition

```typescript
{
  name: 'status',
  type: 'select',
  required: true,
  indexed: true,
  options: [
    { label: 'Active', value: 'active' },
    { label: 'Inactive', value: 'inactive' },
    { label: 'Archived', value: 'archived' },
  ],
  description: 'Current status of the record',
}
```

### Constraints

- **`required`** -- If `true`, the field must be present when creating a resource.
- **`indexed`** -- If `true`, the field is indexed for faster queries.
- **`defaultValue`** -- A default value applied when the field is not provided.
- **`options`** -- Required for `select` fields. An array of `{ label, value }` pairs.

## Links (Relationships)

Links define relationships between Object Types. A link has a name, a target Object Type, and a cardinality.

### Cardinality

| Cardinality | Meaning | Example |
|---|---|---|
| `one-to-one` | Each resource links to exactly one target | Patient → InsurancePolicy |
| `one-to-many` | Each resource links to many targets | Doctor → Patients |
| `many-to-one` | Many resources link to one target | Patients → PrimaryCareProvider |
| `many-to-many` | Many resources link to many targets | Students → Courses |

### Link Definition

```typescript
{
  name: 'encounters',
  targetObjectType: 'Encounter',
  cardinality: 'one-to-many',
  cascadeDelete: false,
}
```

- **`cascadeDelete`** -- If `true`, deleting the source resource also deletes linked target resources.

## Actions

Actions are named business operations that users can perform on a resource. They are not arbitrary API calls -- they are **declared** in the Object Type definition and enforced by the platform.

### Action Definition

```typescript
{
  name: 'submit_intake',
  displayName: 'Submit Intake',
  requiredRole: 'tenant-user',
  validationRules: {
    requiredFields: ['firstName', 'lastName', 'dateOfBirth'],
    requiredStatus: 'draft',
  },
  sideEffects: [
    { type: 'set_field', field: 'status', value: 'submitted' },
    { type: 'set_timestamp', field: 'submittedAt' },
    { type: 'set_user', field: 'submittedBy' },
  ],
}
```

### Key Properties

- **`requiredRole`** -- The minimum role needed to execute the action: `tenant-user`, `tenant-staff`, or `tenant-admin`.
- **`validationRules.requiredFields`** -- Fields that must have non-empty values before the action can run.
- **`validationRules.requiredStatus`** -- The resource must be in this status for the action to be valid.
- **`sideEffects`** -- Automated changes applied when the action executes successfully.

## Side Effects

Side effects are computed values applied automatically when an action runs. They remove the need for manual field updates in application code.

### Side Effect Types

| Type | Behavior | Example |
|---|---|---|
| `set_field` | Sets a field to a static value | Set `status` to `"approved"` |
| `set_timestamp` | Sets a field to the current timestamp | Set `approvedAt` to `"2025-03-15T10:30:00Z"` |
| `set_user` | Sets a field to the ID of the user who performed the action | Set `approvedBy` to `"user-abc-123"` |

Side effects run atomically with the action. If the action fails validation, no side effects are applied.

```typescript
sideEffects: [
  { type: 'set_field', field: 'status', value: 'approved' },
  { type: 'set_timestamp', field: 'reviewedAt' },
  { type: 'set_user', field: 'reviewedBy' },
]
```

## Schema-Driven Development

The Object Type definition is the **single source of truth** for your domain model. This has several practical consequences:

1. **Validation is automatic.** The platform validates every create, update, and action against the published schema. You do not write validation logic in your application.

2. **The CLI is your schema tool.** Use `eai types validate` to check definitions locally, `eai types seed` to push them to the platform, and `eai types diff` to compare local vs. remote state.

3. **Schema changes are code changes.** Modifying a property, adding a link, or defining a new action is a change to `object-types.ts`. It goes through code review, version control, and CI/CD like any other code change.

4. **The API adapts to the schema.** Once an Object Type is published, the resource API accepts and returns data that conforms to the schema. No separate migration step is needed.

<Aside type="tip">
  Run `eai types validate` before every commit. It catches schema errors (duplicate property names, invalid cardinalities, missing required fields on actions) before they reach the platform.
</Aside>

## Complete Example

Here is a full Object Type definition for a patient intake system:

```typescript
export const objectTypes = {
  'patient-intake': [
    {
      name: 'Patient',
      displayName: 'Patient',
      description: 'A patient record for the intake system',
      status: 'published' as const,
      properties: [
        { name: 'firstName', type: 'text' as const, required: true },
        { name: 'lastName', type: 'text' as const, required: true },
        { name: 'dateOfBirth', type: 'date' as const, required: true },
        { name: 'email', type: 'text' as const, required: false },
        { name: 'phone', type: 'text' as const, required: false },
        {
          name: 'status',
          type: 'select' as const,
          required: true,
          options: [
            { label: 'Draft', value: 'draft' },
            { label: 'Submitted', value: 'submitted' },
            { label: 'Reviewed', value: 'reviewed' },
          ],
          defaultValue: 'draft',
        },
        { name: 'submittedAt', type: 'date' as const, required: false },
        { name: 'submittedBy', type: 'text' as const, required: false },
      ],
      linkTypes: [
        {
          name: 'encounters',
          targetObjectType: 'Encounter',
          cardinality: 'one-to-many' as const,
          cascadeDelete: false,
        },
        {
          name: 'referral',
          targetObjectType: 'Referral',
          cardinality: 'many-to-one' as const,
        },
      ],
      actions: [
        {
          name: 'submit_intake',
          displayName: 'Submit Intake',
          requiredRole: 'tenant-user' as const,
          validationRules: {
            requiredFields: ['firstName', 'lastName', 'dateOfBirth'],
            requiredStatus: 'draft',
          },
          sideEffects: [
            { type: 'set_field' as const, field: 'status', value: 'submitted' },
            { type: 'set_timestamp' as const, field: 'submittedAt' },
            { type: 'set_user' as const, field: 'submittedBy' },
          ],
        },
      ],
    },
  ],
};
```
