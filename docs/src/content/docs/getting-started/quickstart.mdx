This guide walks you through the complete workflow of creating a vertical application, from scaffolding to running a local development server. By the end, you will have a working project connected to the EnterpriseAI platform.

<Aside>
  Before starting, make sure you have:
  1. The CLI [installed](/eai-cli/getting-started/installation/)
  2. The [platform prerequisites](/eai-cli/getting-started/prerequisites/) in place (tenant access, approved login, and platform configuration from your administrator)
</Aside>

## The full workflow

<Steps>

1. **Scaffold a new vertical**

   Run `eai init` with a name for your project. The name must be lowercase kebab-case (letters, numbers, and hyphens).

   ```bash
   eai init my-vertical
   ```

   The CLI prompts you for configuration options:

   ```
   ? Vertical name (kebab-case): my-vertical
   ? Display name: My Vertical
   ? Description: My Vertical vertical application
   ? Tenant structure: Single tenant (most common)
   ? Include AI chat? Yes
   ? Include document management? Yes
   ? Auth provider: Entra ID CIAM (recommended)
   ```

   Once you answer the prompts, the CLI clones the Vertical Template, customizes it, and initializes a git repository:

   ```
   Creating My Vertical

   ✔ Cloned from eai-tools/Vertical-Template
   ✔ Updated package.json
   ✔ Generated .env.local
   ✔ Created Object Types scaffold
   ✔ Created deploy-demo.yml
   ✔ Generated CLAUDE.md
   ✔ Initialized git repository

   ✔ Created My Vertical at /Users/you/my-vertical

   Next steps:
     1. cd my-vertical
     2. npm install
     3. eai login — authenticate with Entra CIAM
     4. eai tenant select — only needed if you have multiple tenant-admin memberships
     5. eai provision entra — create Entra app registration for end-user auth
     6. eai env pull — sync app config from cloud
     7. Edit src/eai.config/object-types.ts — define your data model
     8. eai types validate — check your types
     9. eai types seed — push types to platform
    10. eai dev — start local development
   ```

2. **Install dependencies**

   ```bash
   cd my-vertical
   npm install
   ```

3. **Authenticate**

   Log in to the EnterpriseAI platform using your Microsoft Entra ID credentials:

   ```bash
   eai login
   ```

   The CLI starts a browser-based sign-in flow. You will see a message like:

   ```
   Authenticating with Entra CIAM
   Tenant: eaidevmyentepriseai

   Opening your browser to complete sign-in
   ```

   Complete sign-in in the browser. The CLI detects the localhost callback automatically.

   ```
   ✔ Authenticated as you@example.com
   Token expires: 3/10/2026, 2:30:00 PM
   Active tenant: My Vertical (my-vertical)
   ```

   <Aside type="note">
     **External developers**: If you are outside the platform organization, you may need to pass `--tenant-name` and `--tenant-id`. You do not need a custom CLI client ID. See [External Developer Setup](/eai-cli/guides/external-developers/) for details.
   </Aside>

4. **Select the active tenant**

   <Aside type="note">
     Skip this step if you only have one tenant-admin membership — `eai login` selects it automatically.
   </Aside>

   If your account has multiple tenant-admin memberships, choose which one to work with:

   ```bash
   eai tenant select
   ```

5. **Provision Entra app registration**

   Create an isolated Entra app registration for this vertical's end-user authentication:

   ```bash
   eai provision entra
   ```

   ```
   → Provisioning Entra app registration for my-vertical on tenant abc123...
   ✔ Entra app registration created for my-vertical
     Client ID      [written to .env.local]
     Client Secret  [written to .env.local]
   ⚠ The client secret has been written to .env.local and cannot be retrieved again.
   ```

   This writes `ENTRA_CLIENT_ID` and `ENTRA_CLIENT_SECRET` directly to `.env.local`. If the registration already exists, the command detects it and preserves your existing secret.

   <Aside type="note">
     **External developers or manual setup**: If you cannot run this command, your platform admin can provide `ENTRA_CLIENT_ID` and `ENTRA_CLIENT_SECRET` directly. Set them in `.env.local` by hand.
   </Aside>

6. **Pull environment configuration**

   Sync the remaining environment variables from Azure App Configuration and Key Vault:

   ```bash
   eai env pull --include-secrets
   ```

   ```
   ✔ Found 10 config values
   ✔ BASE_URL_PUBLIC_API = https://test-api.myenterprise.ai
   ✔ WORKFLOW_MY_VERTICAL_ID = [from Key Vault]
   ...
   ✔ Written to .env.local (10 variables)
   ```

   <Aside type="caution">
     The `--include-secrets` flag resolves Key Vault references into actual values. Without it, secret values are left as placeholders. You need Azure CLI (`az login`) access to resolve secrets.
   </Aside>

   <Aside type="note">
     **External developers**: If you do not have Azure subscription access, you cannot use `eai env pull`. Create `.env.local` manually with the values your platform admin provides. See [External Developer Setup](/eai-cli/guides/external-developers/#create-envlocal-manually) for the template.
   </Aside>

7. **Edit your Object Types**

   Open `src/eai.config/object-types.ts` and define the data model for your vertical. The scaffold includes a sample `Record` type to get you started. Replace it with your domain model:

   ```typescript
   // src/eai.config/object-types.ts
   export const objectTypes = {
     'my-vertical': [
       {
         name: 'Task',
         displayName: 'Task',
         description: 'A work item to be completed',
         properties: [
           { name: 'title', type: 'text' as const, required: true, indexed: true },
           { name: 'status', type: 'select' as const, required: true,
             defaultValue: 'open',
             options: [
               { label: 'Open', value: 'open' },
               { label: 'In Progress', value: 'in-progress' },
               { label: 'Done', value: 'done' },
             ],
           },
         ],
         linkTypes: [],
         actions: [],
         status: 'published' as const,
       },
     ],
   };
   ```

8. **Validate your types**

   Check that your Object Type definitions follow the platform schema rules:

   ```bash
   eai types validate
   ```

   ```
   Tenant: my-vertical
   ✔ Task — 2 props, 0 links, 0 actions

   ✔ All Object Types are valid
   ```

   If there are errors, the CLI tells you exactly what to fix -- for example, a property with an invalid type or a missing `displayName`.

9. **Seed types to the platform**

   Push your Object Type definitions to the platform:

   ```bash
   eai types seed
   ```

   ```
   ✔ Found 1 types across 1 tenant scope(s): my-vertical

   Tenant: my-vertical → abc123-def456
     ✔ Task (created)

   Result: 1 created, 0 updated, 0 failed
   ```

10. **Start development**

   Launch the local development server:

   ```bash
   eai dev
   ```

   Your application is now running locally and connected to the platform. Open the URL shown in the terminal to see your vertical in the browser.

</Steps>

## What just happened

Here is a summary of what each step accomplished:

| Step | Command | What it does |
|------|---------|-------------|
| 1 | `eai init my-vertical` | Clones the Vertical Template and customizes it for your project |
| 2 | `npm install` | Installs Node.js dependencies |
| 3 | `eai login` | Authenticates you with Entra CIAM via browser PKCE flow |
| 4 | `eai tenant select` | Chooses the active working tenant (only needed with multiple memberships) |
| 5 | `eai provision entra` | Creates an isolated Entra app registration for end-user auth |
| 6 | `eai env pull` | Syncs remaining app configuration from Azure App Config and Key Vault |
| 7 | Edit `object-types.ts` | Defines the data model for your vertical |
| 8 | `eai types validate` | Validates your types against platform schema rules |
| 9 | `eai types seed` | Publishes your types to the platform |
| 10 | `eai dev` | Starts the local dev server |

## Useful commands while developing

Once your project is running, these commands help you iterate:

```bash
# Check what has changed between local and remote types
eai types diff

# List resources of a given type
eai resources list Task

# Create a resource from the command line
eai resources create Task --data '{"title": "My first task", "status": "open"}'

# Verify platform connectivity
eai verify

# Diagnose common issues
eai doctor

# Check who you are logged in as
eai whoami
```

## CLI Help System

The EAI CLI provides comprehensive help at multiple levels:

### Top-Level Help

```bash
eai --help
```

Shows all available commands with examples grouped by workflow:
- **Getting Started** workflow (init, login, env pull, types seed, dev)
- **Development Workflows** (types validate/seed, resources list/get)
- **Deployment** workflow (deploy setup/trigger/status)
- **Machine-Readable Output** examples (--format json, --describe)
- **Accessibility** options (--simple, --no-color)

### Command Help

```bash
eai resources --help
eai resources list --help
```

Shows command-specific options and examples.

### Programmatic Help

For AI coding agents and automation:

```bash
eai --describe > cli-schema.json
```

Outputs complete JSON schema of CLI structure including all commands, options, and subcommands.

### Global Options

All commands support [global options](/eai-cli/reference/global-options/):
- `--describe` — Machine-readable CLI schema
- `--simple` — Accessible plain text for screen readers
- `--no-color` — Disable colored output
- `--color` — Force colored output

Many data-returning commands also support `--format json`.

See [Global Options](/eai-cli/reference/global-options/) for details.
