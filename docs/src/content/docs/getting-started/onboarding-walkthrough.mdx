This walkthrough follows **Acme Corp** as they get onboarded to the EAI platform, from initial setup through to building their first vertical application. It shows exactly who does what, and when.

<Aside>
  Think of the EAI platform like an **apartment building**. The platform admin is the landlord who prepares the apartment. The developer is the tenant who moves in and decorates. The identity system is the building's keycard system. The platform API is the front desk.
</Aside>

## The players

| Who | Role | Analogy |
|-----|------|---------|
| **EAI platform admin** | Sets up the customer's space on the platform | Landlord preparing an apartment |
| **jimmy.bond@acme.com** | Customer developer who will build vertical apps | Tenant moving in and decorating |
| **Identity provider** (Entra ID CIAM) | Shared identity system where all users authenticate | Building's keycard system |
| **Platform API** | Gateway that all requests flow through | Building's front desk / concierge |
| **Type registry** | Stores tenant and data model metadata | Building's directory system |

---

## Step 1: Platform admin sets up Acme Corp

The EAI platform admin does this **once** to onboard Acme Corp as a customer.

<Steps>

1. **Create a parent tenant**

   The platform admin creates a tenant record for Acme Corp:

   ```
   Tenant:
     slug: "acme"
     name: "Acme Corp"
     parent: null  (top-level customer tenant)
   ```

   This is like creating a new company folder in the system. All of Acme Corp's vertical applications will live under this parent.

2. **Create a security group**

   The platform admin creates a security group in the identity provider:

   ```
   Security Group:
     name: "demo.acme"
     description: "Acme Corp tenant administrators"
   ```

   This group controls who has admin access to the Acme Corp tenant. Think of it as the access list for a restricted floor in the building.

3. **Invite Jimmy Bond**

   The platform admin invites Jimmy as an external user in the identity provider:

   ```
   Invitation:
     email: jimmy.bond@acme.com
     type: External user
     add to group: "demo.acme"
   ```

   Jimmy gets an email invitation. He clicks the link, authenticates with his Acme credentials (or creates an account), and he's now a recognized user in the EAI identity system — with membership in the `demo.acme` group.

4. **Set environment configuration**

   The platform admin adds a config entry so the platform knows about Acme Corp:

   ```
   PARENT_TENANT_ID = <acme-tenant-id>
   ```

   That's it from the platform admin's side. Jimmy now has:
   - An identity in the system
   - Membership in the admin security group
   - A parent tenant to work under

</Steps>

---

## Step 2: What Jimmy does NOT need to do

Jimmy does **not** need to:

- Set up his own identity provider (he uses EAI's shared system)
- Configure any cloud infrastructure (EAI provides it)
- Set up app registrations (the platform handles this during vertical provisioning)

He just needs to **accept the email invitation** from Step 1.

---

## Step 3: Jimmy starts building verticals

Once the platform is bootstrapped, Jimmy can create vertical apps. He has two options:

<Tabs>
  <TabItem label="eai-cli (Terminal)">
    ```bash
    # 1. Authenticate — Jimmy signs in via device code flow
    eai login

    # 2. Create a child tenant for the vertical
    eai tenant create
    #    slug: "client-dashboard"
    #    linked to parent: "acme"

    # 3. Scaffold the vertical from the template
    eai init client-dashboard
    cd client-dashboard && npm install

    # 4. Define Object Types in code
    #    (edit src/eai.config/object-types.ts)

    # 5. Push Object Types to the platform
    eai types seed
    ```
  </TabItem>

  <TabItem label="Trial Portal (Web UI)">
    1. Jimmy goes to the Trial Portal
    2. Signs in with Microsoft Entra ID (`jimmy.bond@acme.com`)
    3. Connects his GitHub account
    4. Clicks **"Create New Demo"**
    5. The portal runs an automated provisioning workflow:
       - Creates an app registration for the vertical
       - Creates a child tenant (slug: `client-dashboard`, parent: `acme`)
       - Seeds Object Types (the data model)
       - Creates a GitHub repo from the Vertical Template
       - Configures the repo
       - Seeds environment configuration
       - Registers infrastructure
       - Triggers deployment
  </TabItem>
</Tabs>

Both options achieve the same result — the Trial Portal is guided, the CLI is flexible.

## What happens when Jimmy runs `eai login`

When Jimmy authenticates, here's what happens under the hood:

```
Jimmy's terminal
    │
    ▼
eai login — starts device code flow
    │  Jimmy signs in via browser at microsoft.com/devicelogin
    │  ← Gets Token A (audience: CLI app registration)
    ▼
CLI sends request to Platform API
    │  ← Token A in Authorization header
    ▼
Platform API exchanges token
    │  ← Swaps Token A for Token B (audience: API)
    ▼
Platform API forwards to type registry
    │  ← Exchanges Token B for Token C (audience: registry)
    ▼
Type registry validates Token C
    │  ← Checks: Is Jimmy in the "demo.acme" group?
    │  ← Maps to provisioner role → allowed to create tenants + seed types
    ▼
Request succeeds
```

The chained token exchange ensures that every service in the chain knows **who** the request is for (Jimmy) and **what they're allowed to do** (admin of the Acme Corp tenant), without Jimmy needing separate credentials for each service.

<Aside type="tip">
  As a developer, you never see this chain. You just run `eai login` and everything flows automatically.
</Aside>

## Summary

| Step | Who | What | Where |
|------|-----|------|-------|
| 1a | Platform admin | Create parent tenant `acme` | Type registry |
| 1b | Platform admin | Create security group `demo.acme` | Identity provider |
| 1c | Platform admin | Invite Jimmy, add to group | Identity provider |
| 1d | Platform admin | Set parent tenant ID in config | Environment configuration |
| 2 | Jimmy | Accept email invitation | Email link |
| 3 | Jimmy | Create verticals via CLI or Trial Portal | Terminal / Web |

**Key takeaway:** The platform admin sets up the "apartment" (parent tenant + identity + group). Jimmy moves in and builds whatever he wants (verticals) using the tools provided. He never touches infrastructure, identity configuration, or app registrations directly.
