## Persona

**Role**: Software developer at a litigation firm managing 150+ active cases across multiple practice areas.

Attorneys track case details in personal notes, documents are scattered across network drives, and hearing dates are managed through individual calendar systems. The firm has no centralized view of its caseload, document deadlines, or upcoming court dates. Paralegals spend hours each week compiling status reports by polling individual attorneys.

## Business Problem

Without a unified case management system, critical court deadlines are at risk of being missed, document versions conflict when multiple attorneys work on the same case, and client status inquiries require manual research. The firm needs a single platform where cases are tracked from filing through resolution, documents are organized and version-controlled per case, and hearing schedules are visible to the entire team. This scenario builds a case management workflow that provides firm-wide visibility into case status, documents, and court appearances.

## Object Types

| Name | Key Properties | Links | Actions |
|------|---------------|-------|---------|
| **Case** | `title` (text), `type` (select: civil, criminal, corporate, family, ip), `client` (text), `status` (select: active, pending, closed, on-hold), `filingDate` (date) | one-to-many → CaseDocument, one-to-many → Hearing | `closeCase` |
| **CaseDocument** | `title` (text), `type` (select: pleading, motion, brief, correspondence, evidence), `fileUrl` (text), `confidential` (boolean), `uploadedDate` (date) | many-to-one → Case | -- |
| **Hearing** | `date` (date), `court` (text), `judge` (text), `outcome` (text), `type` (select: motion, trial, settlement, status-conference) | many-to-one → Case | -- |

## CLI Workflow

<Steps>

1. **Scaffold the project**

   ```bash
   eai init case-management
   ```

2. **Authenticate and pull environment**

   ```bash
   eai login
   eai env pull --include-secrets
   ```

3. **Define your Object Types**

   Create the Case, CaseDocument, and Hearing types in `src/eai.config/object-types.ts` (see code example below).

4. **Validate the type definitions**

   ```bash
   eai types validate
   ```

   ```
   Tenant: case-management
   ✔ Case — 5 props, 2 links, 1 action
   ✔ CaseDocument — 5 props, 1 link, 0 actions
   ✔ Hearing — 5 props, 1 link, 0 actions

   ✔ All Object Types are valid
   ```

5. **Seed types to the platform**

   ```bash
   eai types seed
   ```

6. **Create sample resources**

   ```bash
   eai resources create Case --data '{"title": "Smith v. Acme Industries", "type": "civil", "client": "Robert Smith", "status": "active", "filingDate": "2025-03-20"}'
   ```

7. **Start local development**

   ```bash
   eai dev
   ```

</Steps>

## Key Takeaways

- **Firm-wide visibility**: All active cases, their documents, and upcoming hearings are accessible from a single platform, eliminating the need for manual status report compilation.
- **Document organization**: Case documents are categorized by type and linked to their case, with confidentiality flags controlling access to sensitive materials.
- **Court calendar integration**: Hearing records with court, judge, and type data provide the firm with a complete view of upcoming court obligations across all cases.
- **Case lifecycle tracking**: The structured status flow from active through to closed ensures every case is accounted for and properly resolved.
